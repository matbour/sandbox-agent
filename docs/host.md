# Target host

Generic description of the board. LAN addresses, accounts, the other services it runs and access
details are in the private notes (`docs/private/host.md`, not committed).

Checked on 2026-11-11. Re-check values that may drift (kernel version, free memory).

## Hardware and OS

| Item | Value |
| --- | --- |
| Board | Orange Pi 5 Plus |
| SoC | Rockchip RK3588 |
| CPU | 8 cores, big.LITTLE: cores 0-3 Cortex-A55 (`CPU part 0xd05`), cores 4-7 Cortex-A76 (`0xd0b`) |
| RAM | 16 GB, no swap |
| Disk | NVMe, ext4 |
| OS | Ubuntu 26.04.1 LTS, aarch64 |
| Kernel | `7.0.0-42-generic` (Ubuntu stock `linux-generic`), `PREEMPT_DYNAMIC` |

A55 cores are in-order and slower (about 1.8 GHz, 128 KB L2); A76 cores are out-of-order and about
2 to 3 times faster per core (about 2.4 GHz, 512 KB L2). Both implement ARMv8.2-A.

### AppArmor blocks unprivileged user namespaces

`kernel.apparmor_restrict_unprivileged_userns = 1` (Ubuntu default). An unprivileged process can only
create a user namespace if its AppArmor profile has the `userns,` rule. Verified:

```console
$ unshare -Ur id
unshare: unshare failed: Permission denied
```

Ubuntu's fix for other applications is a named profile, for example `/etc/apparmor.d/1password`:

```
abi <abi/5.0>,
include <tunables/global>

profile 1password /opt/1Password/1password flags=(unconfined) {
  userns,
  @{exec_path} mr,
  include if exists <local/1password>
}
```

Ours will live in `deploy/apparmor/` (see [roadmap](roadmap.md), M2). Installing it needs root once.

## Secrets at rest: no TPM (checked 2026-11-15)

- No TPM: no `/dev/tpm*`. The firmware runs no TEE (no OP-TEE node in the device tree, no
  `/dev/tee*`), so there is no firmware TPM either. No eMMC, so no RPMB partition.
- The stock kernel is ready for a discrete TPM: `CONFIG_TCG_TIS_SPI=y`, `CONFIG_TCG_TIS_I2C=m`
  (Infineon driver included), `CONFIG_TCG_FTPM_TEE=m`, `CONFIG_OPTEE=m`.
- systemd encrypted credentials work for user units without a TPM: `systemd-creds --user encrypt`
  seals with the host key (`/var/lib/systemd/credential.secret`, root only, on the same NVMe) bound
  to the user, and `LoadCredentialEncrypted=` exposes the plaintext in a tmpfs (mode 0400) while the
  unit runs. Any process of the same user can decrypt the file too.
- Adding a TPM, if ever: a Raspberry Pi TPM 2.0 board on SPI (Infineon SLB9672) fits. The header's
  SPI0_M2 uses the Raspberry Pi SPI0 positions: MOSI 19, MISO 21, CLK 23, CS0 24, CS1 26 (Orange
  Pi wiki); Raspberry Pi TPM boards use CS1. Power and ground on pins 17, 20 and 25 as on a
  Raspberry Pi: to verify on the board's pinout before plugging it in.
- Enabling it: the board boots U-Boot with `extlinux.conf`, generated by `u-boot-update`
  (`u-boot-menu`), which supports `U_BOOT_FDT_OVERLAYS` in `/etc/default/u-boot`. Ubuntu's DTB has no
  `__symbols__` and only the `spi0m0` pin groups (unused groups are omitted), so the overlay must
  target nodes by path and define the SPI0_M2 pin groups itself (GPIO1_B1 to B5, function 8: to
  verify against the RK3588 pinctrl). It can be checked off the board with `fdtoverlay` before
  anything changes. It changes the boot configuration, so the owner installs it, keeping a boot
  entry without it. Without measured boot, a TPM protects against a disk taken out of the board,
  not against someone who boots the board itself.

## Accounts

- A development account in the `kvm` group (so `/dev/kvm` opens without root), **not** in the
  `docker` group (root-equivalent). Its sudo requires a password typed by a human.
- Later, a dedicated `sandbox-agent` system account for the service.

## The board is not a lab machine

It also runs other self-hosted services in Docker, and their administration credentials live on it.
A sandbox escape, or even LAN access from a sandbox, would expose them. See
[threat-model.md](threat-model.md). This project never modifies Docker or the other services. The board is the manager and the arm64
runner (D42); the network for its Firecracker guests (D44) would add firewall rules next to
Docker's, so it waits for the owner's agreement.

## Ingress

- No inbound port is open. Public traffic arrives through an outbound tunnel (cloudflared).
- The webhook receiver gets a dedicated hostname rule in the tunnel, pointing to
  `http://localhost:<port>`.
- TLS ends at the tunnel provider's edge; the last hop is plain HTTP on localhost.

## Toolchain

Not installed on the board: gVisor (`runsc`), Firecracker, Cloud Hypervisor, bubblewrap, nsjail.
Installed system-wide: `git`, `nft`, `make`, `rsync`.

Go is installed in the development account's home (`~/.local/go`, official tarball, checksum
verified), not system-wide, so the toolchain does not touch the rest of the host. The repository is
checked out in `~/sandbox-agent`. Development itself moved to a separate x86-64 machine (D38): see
[Development machine](#development-machine).

## Development machine

An x86-64 Ubuntu machine where the code is edited, built and tested, including the tests that need
a GPU. Its hardware and access are in the private notes. Toolchain, installed in the home directory
(2026-11-15, official releases, checksums verified):

| Tool | Version | Path |
| --- | --- | --- |
| Go | 1.27.3 | `~/.local/go` |
| gVisor (`runsc`) | release-20261109.0 | `~/.local/opt/gvisor-<version>`, linked from `~/.local/bin` |
| Firecracker, jailer | v1.18.0 | `~/.local/opt/firecracker-<version>`, linked from `~/.local/bin` |
| Cloud Hypervisor, `ch-remote` | v54.1 (static) | `~/.local/opt/cloud-hypervisor-<version>`, linked from `~/.local/bin` |

To upgrade one, unpack the new release into its own `~/.local/opt/<tool>-<version>` and repoint the
link.

It is the amd64 runner of the demonstration (D42). Docker is installed on it (the development
account is not in `docker`), so the network for Firecracker guests (`deploy/network/`, D44) puts
its accept rules in Docker's `DOCKER-USER` chain. Installed on 2026-11-20. The board has none of the three yet (see [Toolchain](#toolchain)).

The same two host settings as on the board stand in the way: the development account must be in
`kvm` for Firecracker and Cloud Hypervisor to open `/dev/kvm`, and unprivileged user namespaces are
blocked by AppArmor (`kernel.apparmor_restrict_unprivileged_userns = 1`), which rootless `runsc`
needs. The fix is a profile that grants only `userns,` to the home-directory `runsc`, installed once
by the owner:

```
# /etc/apparmor.d/sandbox-agent-runsc, loaded with: sudo apparmor_parser -r <file>
abi <abi/5.0>,
include <tunables/global>

profile sandbox-agent-runsc /home/<user>/.local/opt/gvisor-*/runsc flags=(unconfined) {
  userns,

  include if exists <local/sandbox-agent-runsc>
}
```

The glob keeps working across upgrades (one directory per version). It also covers anything the
account writes at that path, which is acceptable on the development machine only; deployed
binaries go in a root-owned path. The exact command and the current state are in the private
notes.
